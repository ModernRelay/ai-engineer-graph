| `el-deferred-tools` | Deferred tools and tool search | technology | context | Context-budget mechanism: tools can be marked **deferred loading** (since GPT-5.4, in the Responses API) so they are absent from the context window and reachable only through a tool-search call — either the built-in tool-search tool or your own implementation "if you feel like you can better do that discovery yourself." | `el-apply-patch` | Apply patch tool | technology | harness | Diff-based file-editing tool that **all models from GPT-5 onward were trained on** — used both to edit and to create files, with a general shell tool for everything else. | `el-codex-sandbox` | Codex sandbox layer | technology | security | All file-system and network interaction routes through a per-platform sandbox: **Seatbelt** on macOS, **Bubblewrap** on Linux, and a **custom open-source Windows sandbox** OpenAI had to build itself (shipped in the same repository; a companion article covers the rejected Windows alternatives). The layer that makes auto-approval decidable rather than advisory |
| `el-auto-review` | Auto review (auto-approval subagent) | technology | security | Answer to approval fatigue and to the "IT and security really hates that you turn on full access" problem. When a sandboxed action escalates, the harness spins up a **read-only auto-review subagent that cannot itself spawn subagents**, and hands it the user authorization, a risk taxonomy, judging criteria, and the transcript plus the pending tool calls. It returns a judgment on authorization strength, blast radius, and disposition — auto-approving the unpredictable-but-benign while holding the line on data exfiltration. Applies symmetrically to file-system and network actions ("curling Google to see if the internet works is fine, but maybe not uploading a file"). Context-sensitivity is the point: deleting a `.git` folder is fine if asked for and catastrophic if not |
| `el-websocket-mode` | WebSocket mode (stateful Responses transport) | technology | inference | Replaces server-sent events over HTTP with a **persistent WebSocket** carrying stateful context, so each turn sends only what changed — a tool call returns just its result rather than replaying every item (demoed as 1 item versus 9). Built because at ~1,000 tok/s "inference was no longer the bottleneck, it was actually the network"; the win compounds across the many tool calls an agent makes |
| `el-goal-continuation-prompt` | Goal continuation prompt | concept | harness | The mechanism under `/goal`: the harness re-injects a **continuation prompt** carrying the user's stated objective after every turn, and keeps doing so until the model calls an update-goal tool declaring the objective met. The operational consequence is a prompting rule — "you don't want to write full essays into your goal, but instead have very concrete and verifiable prompts, so it's easy to detect when things are done" |

| `how-budget-agent-context-explicitly` | Budget agent context with mechanism, not discipline | Treat context construction as a first-class harness stage with three simultaneous targets — size, flexibility and cacheability — and keep the predictable parts (model instructions) structurally stable so the cache prefix survives; assume the unpredictable parts are user-installed (MCP servers inflating the tool registry, an unbounded skills list) and bound them in code rather than by asking users to install less; mark rarely-used tools **deferred** so they cost nothing until a tool-search call retrieves them, and supply your own discovery implementation if you can beat the built-in one; cap any growing list as a **fraction of the context window** rather than a fixed count, and degrade gracefully by shortening descriptions; and remember the reason is quality as much as cost — surplus context raises the odds of self-contradiction, which reads as model confusion | `ReferencesElement → el-deferred-tools`, `el-responses-api`, `el-agent-skills` **[batch1]** |
