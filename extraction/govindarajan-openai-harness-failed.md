| `el-harness-blueprint` | Agent harness blueprint | concept | harness | The architecture the speaker claims is common to every production agent — personal (OpenClaw, Hermes) and coding (Codex, Cursor, opencode, Claude Code) alike: events arrive from many surfaces (chat, webhook, timer/heartbeat, other systems) → a control plane maps each event to a **session key** → the session key defines the state boundary and its **session lane** gives that mutable state exactly one active writer → the runtime calls models and tools → tools act through approvals and policy → the audit trail becomes the run receipt. The runtime itself is stateless: the harness rebuilds the working set (transcript, session state, memory, policy version, tool definitions) every turn, and the model sees only what the harness supplies |
| `el-state-ownership` | State ownership (system of record) | concept | harness | Every fact an agent might use later must have one named owner whose persistent state *is* the truth, and one replay path: a calendar event belongs to the calendar system, a support status to the ticketing system, a code change to the repo/workspace, a conversation turn to the session transcript, a user preference to the memory store. "Storage tells you where the bytes live; ownership tells you who can reconstruct reality." Operational test: for every such fact, who owns it and how would you replay it — if no owner can replay it, the system did not reliably remember it |
| `el-ordered-commit-path` | One ordered commit path | concept | harness | One ordered commit lane per mutable state boundary — queue, mutex, transaction or lock (locks/mutexes across sessions, queues/transactions within one) — deliberately *not* a ban on concurrency: fan-out sub-agents, parallel reads, independent retrieval and many concurrent sessions all stay allowed. Serialization is scoped to commit time, never system-wide. Rejects "last writer wins" as a consistency model: two locally-correct writers doing load-modify-save silently erase each other |
| `el-run-receipt` | Run receipt | concept | harness | Evidence that survives the turn, recording the whole chain — what the model proposed, what policy allowed or denied, what execution attempted (tool/API, arguments, attempt number, idempotency key, external result), and what the **user-visible edge** confirmed or failed to confirm — plus the terminal outcome of every external boundary (success / failure / timeout / cancel / max attempts). | `el-scoped-approval-object` | Approval as scoped execution state | concept | security | Human approval modelled as an object bound to the action it authorized rather than a vague memory that someone clicked yes: who approved, in which session and run, for which tool, for which arguments, for how long, with what outcome, and a pointer to the receipt. | `how-run-receipt-audit` | Run the five-question receipt audit on one production trace | Pick **one** agent system and one real production path, not all of them, and ask for the receipt. (1) *What woke it up?* — user message, webhook, timer, tool result, sub-agent or replay; name the trigger and its identity, or you cannot reason about deduplication, order or authorization. (2) *What state did it inherit?* — transcript, session state, memory snapshot, policy version, tool surface; the model only reasons over the working set the harness assembled. (3) *Which authority did it use?* — actor, session, tool, run, arguments, scope, lifetime; a model request is not permission, and authority should bind to one pending action. (4) *What executed?* — tool or API call, arguments, attempt number, idempotency key, external result: the side-effect boundary, not a summary of intent. (5) *What evidence survived?* — did the ticket update, did the message render, did the file change, does the calendar event exist; the receipt should end at the boundary the user cares about. These questions turn a fluent conversation into an inspectable production run | `ReferencesElement → el-run-receipt`, `el-harness-blueprint` |
| `how-one-ordered-commit-path` | Give every mutable state boundary exactly one ordered commit path | Name an owner (system of record) for every fact the agent may use later and make sure it can be replayed; then give that boundary one ordered commit lane — queue or transaction within a session, lock or mutex across sessions. Keep parallel reads, independent retrieval, fanned-out sub-agents and concurrent sessions. Be conservative at commit time only, never across the whole system. Treat "last writer wins" as a bug, not a policy | `ReferencesElement → el-ordered-commit-path`, `el-state-ownership` |
| `how-bound-every-external-boundary` | Bound the work before the work bounds you | Silence is not a terminal state: give runs deadlines and cancellation, add a watchdog so stuck work is visible, give tools timeouts *and* error results (so a missing result is impossible rather than invisible), and give channels recovery commands that do not queue behind the stuck work they are meant to fix.
