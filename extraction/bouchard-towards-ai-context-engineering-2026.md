| `el-context-mgmt-vs-memory` | Context management vs memory | concept | context | The framing distinction: **context management** = optimizing what the model sees within one session; **memory** = state across sessions (the model is stateless, so a returning student starts from zero unless you build memory). The workshop deliberately scopes to context management first "because you can't have multiple sessions if one session is shitty." What the tutor's context contains: system prompt, tool definitions, chat history, **old tool outputs** (the main scaling bottleneck), retrieved course chunks, and the user question |
| `el-compaction-techniques` | The compaction toolkit | concept | context | The survey of ways to shrink context: trivial no-LLM tools (truncate outliers keeping head+tail, sliding window / trim to last-N turns, always-clear specific tool outputs) and LLM-based ones (**selective retention** — the model decides what to keep/discard; **summarization**; **delta summarization** — Claude Code's running-summary update, useful with sub-agents; full summary-and-reset at the limit). Plus **offload**: save to files/memory (the Karpathy LLM-wiki idea) or RAG. The two that worked best in their experiments: selective retention and summarization — but see the caching caveat |
| `el-caching-makes-compaction-a-trap` | Caching makes summarization a trap | concept | inference | The load-bearing economic insight: providers cache already-sent tokens (KV cache), and cached tokens are far cheaper — **up to ~50× on DeepSeek**, ~90% cost saving typically — and faster (already computed). But **any transformation of the context (summarize/compact) creates a new context the provider can't cache**, so you pay full price for the transformed tokens. Consequence: for compaction to be worthwhile you must compress by **more than the cache multiplier (>50×)** without losing quality — usually impossible — so "summarization is potentially a trap." The most serious harnesses (Claude Code, Codex) use caching plus very specific, non-summarizing compaction |
| `el-keep-everything-wins` | Keep-everything wins (with caching) | concept | context | The headline experimental result across 11 presets, two models (Gemini, DeepSeek V4 Flash), and single/multi-turn tasks: **not touching the context beat every compaction technique on recall, cost, and latency**. Recall: keeping everything answered specific buried facts ~95% of the time vs ~32% after summarizing/compacting (summaries drop the details). Cost: the setup sending the *most* tokens was *cheapest* because ~97% were cached; a 36-turn / 1.78M-token conversation still came out ahead. Latency: compaction forces the agent to re-retrieve information it already had, adding tool calls. Long context held: no context rot on distinctive facts up to ~800k tokens |
| `el-when-to-compact` | When compaction still wins | concept | context | The boundary conditions where keep-everything fails and you must compact/retrieve: **local models** (hardware caps context — a 32k MacBook window can't hold lessons that individually exceed it; raising model *size* doesn't raise the *window*), and **any context exceeding the window**. Their decision rule: "do not compact by default — name the constraint, then choose." Final production choice: DeepSeek V4 Flash (cheapest given cache discount) + hybrid retrieval + keep-everything up to a 30k-token compaction threshold |
| `el-agentic-kb-browsing` | Agent-browses-knowledge-base retrieval | technology | context | The second retrieval tool: instead of only hybrid search, let the agent **browse the knowledge base via sandboxed read-only bash commands** over a raw/generated/wiki folder tree (the wiki built by Claude Code from the raw files, per the Karpathy LLM-wiki idea), with limits (8s command timeout, 40k-char output cap, 20-command ceiling, read-only). Honest finding: it was **used ~90% of turns but produced no recall improvement and was 50% slower** — hybrid search alone was enough for their real (complex) student questions. A negative result kept as a result |

| `how-engineer-context-in-2026` | Engineer context around the cache, and measure it | Separate **context management** (within a session) from **memory** (across sessions) and fix the session first; know that the single most important fact about your setup is its **prompt caching** behaviour — cached tokens can be up to ~50× cheaper and are already computed, but **any compaction or summarization breaks the cache**, so you pay full price for transformed tokens and must compress by more than the cache multiplier to come out ahead, which is usually impossible; therefore **do not compact by default** — when caching applies, keeping the full history often wins on recall, cost *and* latency at once (summaries drop buried-fact recall from ~95% to ~32%, and compaction forces the agent to re-retrieve what it already had); **name your constraint before compacting** — compaction and retrieval genuinely win when the cache doesn't apply (local models capped by a small window, or context exceeding the window), where retrieval is accurate and stuffing the window is catastrophically slow; use **hybrid retrieval** (semantic + BM25), because semantic search alone collapsed to 0% recall on facts buried at 400k tokens while BM25 held 100%; treat fashionable additions (agent-browses-KB-via-bash, GraphRAG) as hypotheses to **measure**, since both tied or lost on real evaluations here while costing more; prefer **many small skills that reference each other** with progressive disclosure over large ones; and **log everything** (tokens, cache-hit rate, cost, TTFT, tool calls, user frustration) because the smart techniques are plausible and often detrimental — you cannot reason your way to the right context strategy | `ReferencesElement → el-caching-makes-compaction-a-trap`, `el-keep-everything-wins`, `el-when-to-compact`, `el-compaction-techniques`, `el-agentic-kb-browsing` |
