| `el-benchmark-anatomy` | Benchmark anatomy (the five-stage reduction) | concept | harness | Deliberately jargon-free decomposition arrived at after hitting "a wall of keywords" (graders, long horizon, verifiers, rubrics): a benchmark is a **prompt/instruction** → fed to **models and agents** → which produce **solutions** → verified and graded by **verifiers and rubrics** → all wrapped in a **harness** that isolates the run from external factors → emitting **trajectories, scores and metadata** used to rank models. Its analytic value is the implied conjunction: the equation only yields a meaningful ranking if *every* stage is sound, so a single weak stage (usually the prompt or the verifier) silently invalidates the score |
| `el-leaky-prompt` | Leaky prompt | concept | harness | Benchmark instruction that hands over the answer inside the task text — distinct from training-data contamination. Two observed shapes: the instruction **points directly at the test file**, so the model has everything it needs to implement against the tests rather than solve the problem; and the instruction **specifies the complete interface** of the intended implementation, locking the model out of any design freedom. Both convert a capability test into an instruction-following test |
| `el-benchmark-task-principles` | Five principles for benchmark tasks (G2i) | concept | harness | Vendor framework for authoring tasks: **(1) human instructions** — authored and reviewed by humans, expressing desired behaviors, objectives and hard constraints rather than implementation detail; **(2) holistic graders** — behavioral tests for broad surface plus precision where it matters (security, business logic get the full unit/integration/e2e stack; the rest doesn't need 100% coverage), mirroring how engineers actually test; **(3) production grade** — economically valuable tasks, judged by whether an engineer can say "if the LLM fixes this, I trust it to fix that"; **(4) contamination-free by design** — novel tasks only plus private hold-out sets, since today's benchmarks are drawn from public repos; **(5) informative leaderboards** — the benchmark must tell a story and support a decision, surfacing the run data instead of only who won |
| `el-leaderboard-trust-gap` | Leaderboard trust gap | concept | harness | The demand-side consequence of benchmark quality problems: "I have not met an engineer in the last 6 months that would choose a model based on the leaderboards." | `ins-benchmark-tasks-must-be-worth-passing` | Task difficulty and task value are independent axes, and the field has been optimizing the wrong one. | `how-author-benchmark-tasks-five-principles` | Author benchmark tasks like production engineering work | Write and review instructions with humans, stating desired behavior, objectives and hard constraints — not implementation detail, and not so much detail that the task becomes self-contained. Grade holistically: behavioral tests for broad surface, full unit/integration/e2e precision only where it matters (security, business logic); don't chase 100% coverage, and never assert on internals or names the instruction didn't specify. Make tasks production-grade and economically valuable — the acceptance test is an engineer saying "if the model fixes this, I trust it to fix that". Make contamination structurally impossible: novel tasks only (everything mined from public repos is already compromised) plus private hold-out sets. Publish leaderboards that tell a story: expose the trajectory and run data behind the ranking, so a reader can act on it instead of digging for their own data points | `ReferencesElement → el-benchmark-task-principles`, `el-original-task-authoring` **[registry]**, `el-observable-behavior-verifier` **[registry]**, `el-private-benchmark` **[registry]** |
| `how-audit-a-benchmark-task-by-hand` | Open the tasks and read them like a pull request | Don't evaluate a benchmark from its leaderboard — pull individual tasks and read the prompt against the test. Does the instruction name the test file or hand over the interface? Then you're measuring instruction-following, not capability. Does the test assert names, variables or structures the instruction never stated? Then you're generating false negatives. Does it exercise unexported internals you'd reject in review? Same. Would you pay for this task to be done at all? Could the answer be recovered from `.git` or a web search instead of solved? Then measure how often models do exactly that. ## Review notes

1. **`pat-benchmark-trust-crisis` — evidence on two legs plus a proposed new one (NOT coined, per instructions).**
   - *Methodology leg*: the hardest **numbers** in the corpus for verifier unreliability — 8.5% false accepts and ~24% false rejects on SWE-bench Pro, with two task-level diagnoses of why. Note these are quoted from Datacurve's published comparison, not measured by G2i (see note 5).
   - *Gaming leg*: reward-hacking rates rising monotonically with model version, with the environment-search channel (`.git`, web traces) named. Joins Shi's 25%/18% git-log rates and Desai's SWE-Marathon arms race.
   - **⚑ Proposed new leg — the crisis is already realized on the demand side.** Every prior data point in the ledger argues that benchmarks *are* untrustworthy. Khial reports that the market has already priced it: not one engineer he's met in six months picked a model from a leaderboard; they read them as hype and test themselves. That converts the candidate from a prediction into an observed state, and it is the exact downstream consequence of the demand-side leg proposed in `heiner-surge-benchmaxxing.md` (buyers can't assess validity → they assess popularity → popularity keeps bad benchmarks dominant → decisions migrate off benchmarks entirely). **Two talks in one batch, from opposite ends of the market (a benchmark seller and a benchmark consumer), describing the two halves of one mechanism.** `sig-engineers-ignore-leaderboards` is the natural rehoming candidate if the pattern is coined; `sig-swe-bench-pro-verifier-error-rates` and `sig-reward-hacking-outpaces-benchmarks` follow.
2. **Same-batch element convergence — `el-two-way-verifier-alignment`.** Coined in the Heiner file (verifiers must check everything the prompt asks, and the prompt must ask for everything verified) and independently exemplified here (tests asserting an unstated variable name; tests on unscoped internals). If you reject that element at review, the Khial edges fold into `el-observable-behavior-verifier` without loss — but the two-independent-statements-in-one-batch fact is worth keeping in the node's brief.
3. **Cross-batch convergence — three vendors, one construction doctrine.** Datacurve (batch 13), G2i (here) and Surge (this batch) independently arrive at: author tasks rather than mine them; verify observable behavior rather than implementation; keep prompts objective-level and short; hold out a private set; and pay real domain experts. Three different business models (data seller, talent company, data seller) converging on identical rules is strong support for `pat-verification-gap` and materially raises the floor under any benchmark-trust pattern. It also means most of this file's value is corroboration, not novelty — priced accordingly in the element count (4 new vs 9 reused).
