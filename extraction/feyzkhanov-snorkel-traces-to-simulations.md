| `el-trace-to-simulation` | Trace-to-simulation | concept | harness | Converting production agent traces into repeatable offline experiments: take real traces, construct benchmark tasks from them, and re-run any agent configuration against a pinned environment with fixed verifiers. Solves the comparability problem that traces and production A/B testing cannot — in production you get a different database state and different tool versions each run, so you "never fully compare apples to apples". Because the environment and evaluators are held constant, the *whole stack* becomes the variable under test (model, thinking level, prompt, harness, skills, tools) and runs go in parallel; the scored axes widen from pass rate alone to cost, latency, and retries |
| `el-private-benchmark` | Private (company-domain) benchmark | concept | harness | The thesis element: every company needs its own benchmark, mimicking its real tools, API services, policies, and workflows, and continuously repopulated from its production traces rather than frozen. Public benchmarks are domain-narrow (SWE-bench = fixing GitHub issues, Terminal-Bench = terminal agents, a computer-use bench = GUI agents) and report pass rate, which measures the model frontier but not a production deployment — "public benchmark is useful to orient and build your prior, but your private benchmark is useful to ship". Serves three jobs at once: pre-release validation, release gate/regression suite, and training set for optimization |
| `el-oracle-solution` | Oracle solution | concept | harness | Reference solution executed through the same task sequence in place of the real agent, authored while constructing the task: it proves the task is solvable at all (if the oracle can't do it, the agent can't) and that the verifiers actually pass a correct run. | `how-build-mini-production-environment` | Build the environment as mini-production, not production | Target "mini production": database, API services, tools, and files must match production closely enough that the agent cannot tell it is in a simulation, without running full production per experiment — think of it as an integration test rig. Mix verification methods by what the check is: deterministic checks work well for final output and tool calls where correctness is cheap to assert; LLM-as-judge, harness-as-judge, or agent-as-judge for trace quality and planning correctness; use one, the other, or both depending on the use case. ## Review notes

Concretely: agents reward-hack simulation environments once they detect them; over-broad verifiers pass incorrect behaviour; incorrect verifiers fail correct behaviour; agent instability produces high-variance scores; and public benchmarks are structurally unable to answer production questions (pass-rate only, wrong domain, wrong tools, no policy coverage).
