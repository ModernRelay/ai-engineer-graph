| `el-floor-vs-ceiling` | The floor versus the ceiling | concept | harness | The talk's organizing distinction. The **ceiling** is the best, most surprising emergent thing your agent can do — "things people would just not expect that it could do." The **floor** is the worst: recommending a competitor, deleting data, or "accidentally sending an AI slop email to a customer because it technically had access to your email." The argument is that the floor is what breaks user trust, and that most publicly visible AI harms — sycophancy being the named example — "are more on the floor side rather than the capability side." Formalized as a customer-segmentation question: **are you a benchmark-maxxer or a floor-raiser?** |
| `el-evals-as-code` | Evals as tests, not datasets | ops | harness | The methodological claim. Eval discourse is "still stuck in the chatbot era" — build a 1,000-row dataset and check the string contains the right answer — which worked when "you knew the answer to most questions your users would ask." It fails now because "the prompt is actually the whole thing: it's all the code, it's your whole harness," and curated eval sets "break as soon as you have a new model or you switch harnesses" (switching to Claude Code CLI is given as an example that invalidates 80% of tool-calling evals). The prescription is that evals should look like **unit and end-to-end tests kept in code and run locally**, citing Sentry's Vitest-evals package and OpenAI's "macro evals" as the same idea under different names. The trade-off is stated bluntly: "you want more safety but you don't want theater" — nobody actually delays a model upgrade two weeks to update evals |
| `el-issue-not-cluster` | Clusters are not issues | concept | harness | The first production lesson, and the most transferable. The naive approach takes all traces and clusters them, which "is useful for one-off analysis but doesn't really scale well." Two structural defects: clusters are hard to track reliably over time (temporal clustering being a research problem in itself), and you do not control the boundaries — "wrong price quoted" and "wrong refund calculated" collapse into a "price issues" cluster despite having extremely different root causes. The analogy given is telemetry: nobody clusters ordinary logs, because what you actually need to know is **when something started and how much it has grown** |
| `el-issue-onset-and-blast-radius` | Onset and percentage of users | concept | harness | What a production agent issue must carry to be actionable, argued as obvious-but-neglected: **when it started** and **what percentage of users it affects**. The first is what turns a report into an investigation — "if I tell you this issue started yesterday, suddenly your mind starts turning: what did I do, what changed, did we change model?" — and the second is the difference between three users and 100,000. Motivated by the claim that "agents will have an infinite number of problems… that's the great and terrible thing about them," so triage, not enumeration, is the job |
| `el-code-mode-over-traces` | Code mode over traces | technology | harness | The scaling technique: apply the code-mode idea familiar from MCP to trace analysis — write classifiers as code, run them in a sandbox, and run them at production scale rather than feeding traces through a model. Paired with the complementary lesson on anomaly detection: **"agents are very, very bad at anomaly detection — don't ask your agent to find anomalies, ask it to investigate anomalies you've already found,"** with as much as possible pulled out deterministically (keyword frequency is the example) so there is something tractable for an agent to investigate |
