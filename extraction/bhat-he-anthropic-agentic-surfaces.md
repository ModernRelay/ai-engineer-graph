| `el-managed-agent-primitives` | Agent, environment, session | concept | harness | The three primitives managed agents is designed around. **Agent** — model, prompts, tools and skills defining what it does. **Environment** — the container it runs in, reusable across sessions with isolated instances, and the place network boundaries are set. **Session** — the combination, persisted as a durable cloud resource recording every interaction, with four states: *idle*, *running*, *rescheduling* on a retryable error, and *terminated* when unrecoverable. Durability is what makes long-horizon reliability possible: the agent can always return to a session and resume |
| `el-durable-session-log` | The durable session log | technology | harness | The single mechanism three separate capabilities are built on. Every event — user message, model response, tool execution, result — is written play-by-play to a persisted log. Surfaced in a UI it becomes **observability**; read back in slices it becomes **context recovery**, solving the problem that in traditional harnesses "the context window and the session are one and the same," so discarded context is unrecoverable — here Claude can re-read what it dropped; and fed to a batch process it becomes the substrate for **memory and self-improvement** |
| `el-dreaming` | Dreaming | technology | context | The frontier feature, and the batch's fourth independent use of the term: take the agent's daily session transcripts plus its current memory state, run a **periodic batch process** over them, and extract new insights and organized structures that edit the memory — "to make the next day's agent sessions automatically much more intelligent. Positioned alongside memory as "two cornerstones of a new frontier unified memory system," with a third form flagged as emerging: **organizational-scale memory** storing a team's runbooks and details |
| `el-outcomes-grader` | Outcomes (rubric-graded retry) | technology | harness | The second frontier feature: the developer defines success criteria and failure cases as a rubric, and a **separate grader agent runs alongside the agent loop**, checking whether the task was actually accomplished. Framed as moving toward "a world where we can have an agent understand what success actually means for a task and have a mechanism to keep iterating," unlocking tasks that were not possible months earlier |
