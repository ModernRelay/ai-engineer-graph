| `el-metr-time-horizon` | METR time horizon | technology | harness | Benchmark methodology that expresses model capability as the length of human work it can complete: a threshold pair of success rate and human hours (e.g. "16-hour threshold at 50%" = solves, half the time, tasks that take a human 16 hours), backed by a rigorous protocol for timing the humans. The de-facto industry yardstick for "long horizon" and the reference the talk measures published benchmarks against |
| `el-long-horizon-dual-metrics` | Human horizon vs model horizon | concept | training | "Long horizon" is a **scalar, not a category** — useful for ranking tasks, not for a binary label, and the threshold moves every year. Two incommensurable rulers: the *human* ruler (expert-hours per task) and the *model* ruler (tokens consumed, steps, tool calls per trajectory). The model ruler is noisy — token counts swing with model family and harness — but it tracks real agent difficulty (context limits, compaction, coherence over steps) and defines the technical frontier. The human ruler breaks down in the opposite place: at the top-10%/1%/0.1% expertise tail, and on tasks that are tedious-but-trivial for a model (a day of Excel reformatting a model solves with a Python script). Use both |
| `el-environment-complexity-axes` | Environment complexity axes | concept | training | Three axes that determine whether an environment actually measures capability. **(1) Tool coordination** — how many tools/external dependencies the agent must move information across (Grafana logs, GitHub CI/CD, CloudWatch, databases) vs the single-file-read world of earlier tasks. **(2) State change** — how much the environment mutates during the task, splitting into *parallelizable* complexity (fan sub-agents over a codebase, merge results; no state coupling) and *sequential* complexity (a bad early query or misread dashboard cascades into every downstream step). **(3) Ambiguity** — how underspecified the opening instructions and artifacts are, forcing exploration the way real work does. Corollary: chaining unrelated independent tasks makes a trajectory long without measuring anything more |
| `el-judge-with-environment-access` | Judge with environment access | concept | harness | The judge/critic is an agent, not an LLM call: it is given the same harness and tools the trained agent had, with **read-only** permissions, so it can verify the *final state* of the environment (did the PR merge, did the redeploy actually go green in the CI/CD and cloud logs) rather than trusting the agent's self-reported tool calls, which are "usually not very reliable". Safeguard requirement: the judge must not be able to mutate the environment after the rollout — no triggering deployments, no writes |
| `el-queryable-trajectory` | Queryable trajectory | concept | harness | As trajectories lengthen, stuffing the whole trace into a judge's context window stops working. Instead process the trajectory into something searchable: store it (e.g. in a database), enrich it with sub-agents, segment it into phases (log triage → code edit → post-change verification), and tag candidate failure points, so the judge-agent can navigate to the critical steps and adjudicate them |
| `el-dynamic-eval-rubrics` | Dynamic evaluation-time rubrics | concept | training | Emerging rubric/judge patterns beyond static grading. Deterministic verifiers are *not* dead — they run in tandem with judges, generating artifacts and metrics for the judge to read. Rubrics can be generated at evaluation time rather than fixed in advance, and can grant **conditional partial credit** by accepting the model's earlier (wrong) assumption and grading the remainder on top of it — "like grading a test where you assume the first part was right and check whether they got the rest right". ⚠ merge-check vs `el-deterministic-partial-grading` **[registry]** (batch 11) |
| `el-environment-learnability` | Environment learnability | concept | training | Whether a model can actually learn from an environment, measured before spending training compute: density of the reward signal (how granular the rubric is), the task distribution, and the quality of the underlying data. Key tension — over-dense rubrics on frontier problems the models cannot yet solve are applied *inconsistently* by judges, so rubric density has to stay inside what the judge can reliably apply; an unlearnable environment just burns compute |

| `ins-length-is-not-difficulty` | Duration is the wrong instrument. You can manufacture an arbitrarily "long-horizon" task by chaining unrelated independent subtasks and learn nothing about the model; what measures capability is **state coupling** (early decisions constraining later ones), **tool-coordination breadth**, and **ambiguity at the start**. Environment design, not task length, is the capability instrument — which is why benchmark comparisons on average-hours are close to meaningless without the complexity profile | `HighlightsPattern → pat-verification-gap` **[registry]** | `ReliesOnElement → el-environment-complexity-axes`, `el-long-horizon-dual-metrics` |
| `ins-the-verifier-is-the-hard-part` | In a long-horizon environment the verifier, not the task, is the expensive artifact: the judge inherits the agent's tools, harness and state access (read-only), needs its own trajectory-processing infrastructure, its own rubric-consistency QA, and its own reward-hacking defences. Verification cost scales with environment complexity — so the binding constraint on training data for non-verifiable domains is verifier engineering, not task supply | `HighlightsPattern → pat-verification-gap` **[registry]** | `ReliesOnElement → el-judge-with-environment-access`, `el-queryable-trajectory`, `el-environment-learnability` |
| `ins-realism-vs-gradeability` | The central design tension of environments: ambiguity is what makes a task resemble real work (humans never start with complete information, and exploration is the skill being tested), and ambiguity is exactly what multiplies the number of valid solution paths — which makes standardized evaluation "much, much harder".
