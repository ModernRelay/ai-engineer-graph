Shape of the talk: a systems argument in three moves. (1) RL post-training is discussed as an *algorithms* problem but at scale becomes a *physical* one — it demands enough GPUs, in one region, on fast fabric, available now, and only the trainer actually needs that shape. (2) The rollout fleet can therefore leave the cluster, if the weight-sync link shrinks — which it does, because **less than 1% of rollout-visible weights change per step** once Adam's step size is compared against the rounding floor of the serving dtype. (3) Given a cheap, bitwise-exact delta, scattered global inference capacity becomes one elastic rollout fleet — implemented as **Stitch**.

## Elements (7 new)

| slug | name | kind | domain | brief |
|---|---|---|---|---|
| `el-cathedral-vs-bazaar-compute` | Cathedral vs bazaar compute | concept | infra | The framing device for the capacity mismatch. The **cathedral** — one region, fast interconnect, many GPUs wired together — is the right shape for a trainer and the hardest thing to get. The **bazaar** — different providers, regions, prices and availability — is where most usable compute actually lives. RL's default loop demands the cathedral for the whole system, so it inherits the scarcest resource's constraints: "RL wants all four of these at the same time — enough GPU, same region, fast fabric, and available now. Any of these is manageable, but all four is pretty hard." Underneath sits the asymmetry that training capacity is not elastic the way inference capacity is: "you cannot assume you can grow the trainer cluster halfway through a run just because rollout wants more nodes" |
| `el-rollout-serving-island` | Rollout serving island | concept | training | The unit that turns out to be movable. Training is one tightly coupled job — every step has collectives, all-reduce and model-parallel communication, which genuinely want RDMA — but **rollout is a fleet of serving jobs with no global all-reduce between them**. So the thing that leaves the cluster is not backpropagation; it is the rollout island: a coherent endpoint or local group of endpoints serving one policy version, free to keep local parallelism and prefill/decode disaggregation inside itself. Across islands the dependency collapses to two directions: policy version in, trajectories and metadata out |
| `el-adam-absorption` | Adam absorption | concept | training | Why the weight-sync link can shrink by three orders of magnitude. Two ingredients. **The floor**: the optimizer keeps high-precision master weights, but the rollout engine serves a low-precision *view*, and a BF16 value only changes if the update crosses the nearest rounding boundary — roughly half a ULP, about θ/256, ≈0.0039 for weights near 1. **The push**: an Adam step is the learning rate times a normalized direction (the raw gradient is divided by running gradient statistics), so the per-weight push is bounded on the order of the learning rate — at RL post-training rates, ~3e-6. The push is more than a thousand times smaller than the floor, so the served value does not move. Crucially this is *not* a claim that the master weights are frozen: "it is saying the value that the rollout engine would serve does not change." Small weights move; large weights absorb their updates |
| `el-sparse-weight-delta` | Sparse rollout-weight delta | technology | training | The object shipped instead of a checkpoint. Cast weights to the dtype the rollout engine serves, diff version *t−1* against version *t*, and encode changed positions plus replacement bits and metadata — via selective override, XOR, or any lossless scheme. Because the patch is **bit-level equivalent rather than a floating-point addition, there is no additive delta drift**: a rollout engine applying it reconstructs the synced served version bitwise. Shrinks the cross-region link from ~500 GB to ~500 MB, i.e. from minutes-to-hours down to seconds. Measured across model families at **~99% of parameters bit-identical per step**, and the property survives staleness — a lagging rollout still has a small changed set. Lower serving precision makes it stronger: the visibility floor scales as θ/2^(mantissa+1), so FP8 and NVFP4 change even less than BF16 |
| `el-rollout-weight-version` | Immutable rollout weight version | concept | training | The synchronization contract that replaces "the current checkpoint." After each optimizer step the trainer publishes an **immutable, named version** to a shared bulletin board; requests become version-aware, stating which version to serve and which versions are acceptable, and responses carry the version back alongside tokens, logprobs, router-replay information and metadata — "exact same information as if they are in the same cluster as the trainer." Artifacts are materialized in Hugging Face safetensors layout so any standard engine can load and shard them itself, which is what keeps the scheme engine-agnostic across SGLang, vLLM, attention backends, parallelism strategies, serving dtypes and GPU generations |
| `el-version-aware-sidecar` | Version-aware rollout sidecar | technology | infra | The small piece of machinery that makes an ordinary, unmodified rollout engine participate. Three cases: if the engine is already at an acceptable committed version, the sidecar proxies the request; if it is behind but can catch up, it applies the missing transitions; if it cannot, it returns **not ready**. That last case is what makes the fleet genuinely elastic — any idle GPU anywhere can be enrolled, and a straggler degrades to unavailable rather than to silently-wrong |
| `el-stitch` | Stitch | product | infra | Modal's concrete implementation of the whole protocol: the trainer side publishes what defines a rollout weight version and records it on the bulletin board; the rollout side pulls the latest weights and self-syncs across regions and providers. Deliberately **framework-agnostic about trainer, engine and transport**, and described as async-first and agentic-first. The payoff claim: rollout engines autoscale globally, each self-syncing and returning rollout metadata, so "scattered inference capacity became one elastic rollout fleet… inference capacity can now become RL capacity" |
