| `ins-training-integrity-needs-verifiers` | At hundreds of billions of parameters across thousands of GPUs, the dangerous failures are the silent ones: a broken GPU corrupting data, a default BF16 accumulation quietly running out of precision, an open-source kernel randomizing half a percent of your gradients. None announces itself; each is only visible as a shape in a loss curve or a gradient norm you happened to be watching, and each can cost a training run. The team's stance — "we don't trust anything" — turns into engineering by hunting **checkable invariants** (replica weights must be identical; gradient norms should trend down) and crashing the run the moment one breaks. | `ins-synthetic-data-as-projection` | The case for synthetic data here is not volume, it is **re-projection**: organic data already contains the rationale, the planning and the structure you want the model to learn, but implicitly and in a form that is often not the most teachable. Synthetic generation extracts those features and projects them onto new planes, which is simultaneously a way to fill gaps and to regularize *how the model is taught* rather than merely what it is shown. Two consequences follow. First, ambition is bounded by difficulty, not by the teacher model: "if the task is too hard for your model, your model will fall on its face — lose correctness, lose diversity", so you decompose until each step is easy, which is precisely how orchestrated pipelines escape the ceiling of what a single teacher model can produce. | `how-compose-synthetic-pipelines` | Compose synthetic pipelines from six parts and four shapes | Treat every pipeline as the same six components — seeds, primary inputs, metadata, secondary inputs, a generator function (prompt template or tool-using agent), and supplementary functions (filters, validators) — then pick a point on the complexity axis per data class: cheap, seed-heavy, small-model pipelines for bulk (where output quality rides almost entirely on seed quality, so invest there), orchestrated multi-agent workflows only where the data justifies the cost. Four shapes cover most of it: **rephrasing** (break token repetition; ablate against the repeated-seed baseline); **multi-stage decomposition** (don't generate the novel — generate setting, characters, styles, plot and twists first, then the chapters; aggregate the processing and build the generation up); **cross-domain porting** (translate between modes — code to another language, math problems into code); and **multi-turn loops** (two agents in conversation, or a judge and an evolver alternating for *k* rounds). Governing rule of thumb: if a task is too hard for the generating model it loses both correctness and diversity — break it down and make each step simpler, which is what frees you from the ceiling of whatever the teacher model can do in one shot. Run it on infrastructure that makes this configurable: a queue of agents with per-agent prompt/parameters/model and entry, exit and frequency rules; orchestrators between agents to impose hierarchy, rewrite the next agent's instructions and route or skip agents; and a supervisor with a global view policing the orchestrator | `ReferencesElement → el-synthetic-pipeline-anatomy`, `el-poolside-hive`, `el-rephrasing-synthetic-data` |
| `how-detect-silent-training-corruption` | Assume the training stack is lying to you, and instrument invariants | Treat data quality and training-codebase correctness as one problem, not two — "if you've got data that sucks you can't train a good model; if you've got a training code base that sucks, you also can't". Then find invariants you can actually check and enforce them: under distributed data parallel every replica must hold identical weights, so hash the weights per replica, compare periodically, and **crash the run on any mismatch** rather than letting it continue — that is what surfaces silent data corruption from a single bad GPU. Watch gradient norms next to the loss, not the loss alone: a run that flattens with a rising gradient norm is a numerics story, and the specific one to check is accumulation precision at the unembedding — activations grow during training, BF16 accumulation under tensor parallelism eventually runs out of precision, and the fix is to move that accumulation to FP32 and resume from the last good checkpoint. Audit third-party kernels the same way: FP8 GEMM kernels produced illegal memory accesses, NaN gradients, and a silent ~0.5% random-value gradient corruption. Know your blind spot — real runs have no replicas sharing both weights and data, so forward/backward equivalence and kernel race conditions escape the hash check entirely; build a redundant dry-run checker to cover it | `ReferencesElement → el-model-replica-hashing`, `el-deepgemm`, `el-laguna-models` |
