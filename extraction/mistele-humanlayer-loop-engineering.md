| `el-agentic-control-loop` | Agentic control loop | concept | harness | An agent loop built to the control-theory template instead of `while true`: a **set point** (desired end state of the codebase with respect to one property), a **sensor** that measures current state (deterministic — ast-grep, ESLint rules, Packwerk — or non-deterministic — an agent plus a skill and natural-language rules — or a pipeline mixing both), the **measured error** (the violation list), a **controller** that turns that error into a control signal about one incremental change, and an **actuator** that applies it, all while the system takes **disturbances** (teammates shipping). Because the components are agents, the lines blur in practice: a hybrid sensor+controller (e.g. React Doctor, which reports the problems *and* the top three fixes) or a merged controller+actuator (one agent picks the change and makes it in the same context window) are both normal. The controller is the load-bearing part — without a well-tuned one the loop makes too large a change or the wrong change, repeatedly. Precedents named as existing control loops: thermostats, Kubernetes autoscaling, infrastructure-as-code, Postgres autovacuum, React's virtual DOM |
| `el-ast-grep` | ast-grep | technology | harness | Language-agnostic structural code search/lint used as a deterministic loop sensor: a rule matches the unmigrated code pattern, granular include/exclude paths scope it, extra rules layer on over time for other patterns to remove, and it works across a multilingual monorepo. Explicitly chosen over an agent, ripgrep or TypeScript-native tooling because it is **out of band** from tsconfig and ESLint — the config an agent will happily disable with an inline comment. Raw output is ~50 keys per violation, filtered to ~4 and sorted deterministically before it reaches the controller |
| `el-golden-patterns` | Golden patterns | concept | harness | Idiomatic reference implementations written **by hand, by humans, before the loop is turned on**, and shipped inside the actuator's skill. Rationale: agents are pattern replicators, so without golden patterns the loop reproduces whatever is in the docs or in the model's memory of the internet rather than your house style. The skill should also carry a response template; expect to iterate the skill from what actually works rather than front-loading it |
| `el-loop-flow-control` | Loop flow control | concept | harness | Adaptive throttling that keeps a loop from outrunning human review: every loop labels the PRs it creates, and before doing any work the workflow checks whether any PR carrying its label is still open — if so it shuts down immediately (before checkout and dependency install). Invariant: at most one open PR per loop, no stacking, no duplicated work, few conflicts. The reasoning is explicitly about review capacity, not compute: an open PR means no human has reviewed the loop's last output, so there is no reason to manufacture more |
| `el-loop-feedback-file` | Loop feedback file | concept | harness | A markdown file tracked in version control that is deterministically loaded into the actuator agent's context on every run (after the controller). A `/iterate` comment on one of the loop's own labelled PRs triggers the workflow to load the PR context — diff, comments, review comments, description — alongside the skill and instruct the agent both to fix the code **and** to update the feedback file. Turns re-steering from a checkout-edit-commit-push chore into a PR comment, and makes the steering history diffable and revertible |

## Insights (2 new)

| slug | name | HighlightsPattern | ReliesOnElement |
|---|---|---|---|
| `ins-loops-need-a-controller` | Loop engineering doesn't need new theory, it needs an old one. What separates a loop you can run on a real codebase from a "blind" one is whether you can name its set point, sensor, measured error, controller and actuator — and above all whether the controller exists and is tuned, because a loop with no controller makes too large a change or the wrong change and then repeats it. The payoff is not only safety: an incremental, well-instrumented loop produces diffs small enough that humans keep reading the code, and a control signal carrying telemetry makes the loop improve the code it touches instead of transliterating it | `HighlightsPattern → pat-harness-over-model` **[registry]** | `ReliesOnElement → el-agentic-control-loop`, `ReliesOnElement → el-golden-patterns` |
| `ins-review-capacity-throttles-loops` | The scarce resource governing an agent loop is human review capacity, not tokens or compute. If nobody has reviewed the loop's last PR, another iteration only manufactures work nobody wants — so the loop should read its own labels and refuse to run. Scaling then happens along axes that respect that constraint: batch 3–5 items per run with a separate implementation phase (and context window) each — cheaper *and* more reliable — or run the workflow N times and hand one PR to each of N teammates, rather than letting one loop stack N PRs on one reviewer | `HighlightsPattern → pat-verification-gap` **[registry]** | `ReliesOnElement → el-loop-flow-control`, `ReliesOnElement → el-loop-feedback-file` |

| `how-build-agentic-control-loop` | Build the loop as a control loop | Ask three qualifying questions first: can you measure the thing, can you apply changes incrementally, can you get feedback on change quality?
