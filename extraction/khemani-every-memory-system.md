## Elements (6 new)

| `el-running-profile` | The running profile | technology | context | The architecture both leading assistants converged on. Every few days (ChatGPT) or every 24 hours (Claude), a background process reads recent conversations, extracts what matters, and rewrites a persistent profile that is then injected into the context window of **every** new conversation. ChatGPT's is ~4,000 tokens across 16 sections and written as **extremely dense keyword clusters** — "almost like clues," relying on frontier models' ability to infer context from limited information. Claude's is ~1,000 tokens of complete sentences. Introduced in ChatGPT V2 (April 2025) and Claude V2 (September 2025) |
| `el-memory-fact-list` | The user-editable fact list | technology | context | The first serious memory implementation (ChatGPT V1, February 2024): the user asks the model to remember something, it extracts a fact ("the user is vegetarian"), stores it in a visible list, and injects the list into every conversation. Two structural flaws named: the **burden of memory management fell on the user**, who had to curate memories while trying to have a conversation; and **staleness** — facts true when written ("Shlok is going to Bengaluru") persist indefinitely. Deprecated by ChatGPT in mid-2026 once the running profile and conversation-search tools superseded it |
| `el-conversation-search-tools` | Conversation-search tools | technology | context | Claude's V1 (August 2025) approach, and the architectural opposite of a profile: **no** stored profile and no fact list, but two tools — search past conversations by keyword or topic, and search by time period ("what did we discuss last week"). Every conversation starts fresh with no user context, and the model retrieves on demand when it judges it needs to. ChatGPT later added an equivalent tool, completing the convergence from both directions |
| `el-memory-convergence` | The memory convergence | concept | context | The survey's central finding: after three years of **independent** evolution from opposite starting points — ChatGPT from stored facts toward retrieval, Claude from retrieval toward a stored profile — both now have a running profile that is visible and editable, plus tools to search past conversations. Gemini has a running profile too, but with detailed per-memory timing logs. The general architecture converged; **the implementation details did not**. Notably, neither uses the RAG-chunk-and-embed approach the industry assumed was the answer: "it wasn't too long ago that everyone, including me, assumed that RAG was the way to go about memory" |
| `el-memory-compute-tradeoff` | Memory as a function of compute | concept | context | The economic frame that explains the design differences. A running profile has two costs: **maintenance** (how often you update it × how much compute per update) and **serving** (it sits in every context window, so length is a per-conversation tax). The ideal system — update after every conversation, spawn subagents for the update, store 400,000 tokens instead of 4,000 — is unavailable "because we live in a GPU-constrained world." The two vendors take **exactly opposite** trade-offs: ChatGPT 4,000 tokens updated every few days (high serving, low update), Claude 1,000 tokens updated every 24 hours (low serving, high update) |
| `el-context-acquisition-gap` | The context acquisition gap | concept | context | The closing argument, and the one the speaker calls a rant: memory quality is capped not by architecture or compute but by **how much context the system can gather**. The worked example — a profile records travel to both Thailand and Turkey with overlapping dates, because the source was a conversation *deciding between them*; the actual decision was made in person, and the corroborating evidence (flight and hotel bookings) sat in connected email the assistant does not reason over. The sharper complaint is not the missing data but the missing curiosity: "what really bothers me is that it doesn't realize there is a conflict. It's not curious about trying to fill in gaps." Diagnosed explicitly as "not a technology problem, it's a product problem," compounded by fragmentation — every chatbot, vertical app, agent and hardware device builds its own private memory, none shared, all rebuilt from scratch |

| `how-design-a-memory-system` | Design memory as a compute budget, and build it in-house | Do not reach for RAG by default — neither leading assistant chunks-and-embeds conversations, and the architecture both converged on is a **running profile** synthesized in the background plus tools to search past conversations on demand; keep memory synthesis **asynchronous** so the user is never made responsible for curating memories while trying to have a conversation, which was the flaw that sank the first-generation fact list; budget memory explicitly as compute, trading update frequency against profile length, since the profile is injected into every conversation and its length is a per-conversation tax while its freshness is an update-cost tax — the two leading vendors sit at opposite corners of that trade-off and both are defensible; decide deliberately how dense the writing is, since keyword-cluster profiles pack more per token and lean on the model's inference while prose profiles are more legible to users; **make the profile visible and editable**, and treat an edit as triggering a resynthesis rather than a patch; design for **staleness** from the start, because facts true when written stop being true and the corpus of failures here is mostly stale-fact failures; build memory in-house alongside the product rather than outsourcing it, because the converged part is easy and the divergent part is product-specific; and invest in **context acquisition and conflict detection** — reason over the sources the user has already connected, and make the system notice and try to resolve contradictions rather than storing both | `ReferencesElement → el-running-profile`, `el-memory-compute-tradeoff`, `el-context-acquisition-gap`, `el-conversation-search-tools` |
