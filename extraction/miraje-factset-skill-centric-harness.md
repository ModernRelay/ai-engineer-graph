| `el-skills-as-features` | Skills as features | concept | harness | The talk's thesis. When the agent becomes the product's main interface — the user talks to it, or it decides behind the scenes how the user navigates — the question "where do features live?" gets a new answer. Framing offered: **prompts define who the agent is, tools define what it can connect to, skills define how a task gets done** — and *how* is where the business logic that shapes agent behaviour belongs. Worked case: equity research and wealth management, two core finance workflows that used to be screens, buttons and dropdowns, are now **merely skills**. Two consequences he draws: a skill can be shipped by **anyone in the company who understands the product**, not only engineers; and the **engineer's role shifts from shipping features to shipping harnesses** — "smooth vehicles for your skills to run" |
| `el-skill-registry` | Skill registry | framework | harness | The minimum viable implementation of skill support in a custom harness — **three things**: a skill registry (a collection of skills as name, description and path), a system prompt, and a basic **file-read tool** (plus bash or a code sandbox only if skills ship executable scripts). Discovery works by concatenating each skill's name, description and path into the system prompt — **never the body** — so the agent reads only the bodies it selects, which is `el-progressive-disclosure` in its literal form. Around it sits a plain agentic loop: keep a messages array, call the model with messages and tools, append every tool call, terminate when a turn produces none |
| `el-skill-routing-descriptions` | Descriptions as routing signals | concept | harness | The most operational lesson: **skill descriptions are routing infrastructure, not documentation**. Demonstrated with two near-identical skills (report-HTML and report-PDF) where only the description — "use this skill only when the user asks for a PDF report" — decides which fires; *PDF* is the trigger word. Rules: write descriptions **about the user's request, not about the skill itself**; keep them **distinct enough** that the agent doesn't get confused; don't let them go **stale** — those three are the reasons skills fail to trigger. In agentic products (unlike coding harnesses) skills are almost entirely **model-driven**, because non-technical users cannot be asked to carry the cognitive load of remembering which skill to invoke |
| `el-skill-library-governance` | Skill library governance | ops | harness | Five aspects, each answering one question, all borrowed from decades-old code practice. **Admission** — should this skill exist at all or fold into an existing one? (an automated gate on the registry with a human in the loop, analogous to PR review). **Ownership** — who maintains it? (named skill owners, like CODEOWNERS; skills maintained by the same application teams that maintain the features). **Boundaries** — **allow-listed, access-controlled tools per skill**. **Lifecycle** — semantic versioning, deprecation warnings, changelogs. **Coherence** — periodic audits and skill-validation checks so a large library still makes sense, the way features cohere in a good product. Framed against the objection: governance "doesn't need to be a red-tape bottleneck — it depends on how much automation is in place with proper human in the loop" |
