| `el-saga-orchestration` | Agentic saga orchestration | concept | infra | The existing saga orchestrator — the layer that already sequenced distributed transactions across bounded contexts — is where the agentic tier is installed, as sub-orchestrators (tier 1 deterministic, tier 2 agentic) rather than as a new service. ## Review notes

1. **`pat-durable-execution` — which side this lands on (per the extraction brief).** It lands on **both, split by layer**, and the split is the interesting part:
   - *Supporting the substrate claim:* this is a production system whose ground truth is an append-only, replayable event log, with agents reading projections of it — the same architecture as `el-agent-session-log` (Omnara, b9), `el-activegraph` (BabyAGI 4, b10) and `el-chronicle` (Microsoft, b8), arrived at independently from the enterprise/DDD tradition rather than from agent research. That is a genuinely new *provenance* for the thesis: the corpus's other data points are all agent-native vendors.
   - *Counter to the vendor-category claim:* every durable component here is stock enterprise infrastructure the business already ran — Cosmos DB, a change feed, a message broker, a saga orchestrator. Nothing new was bought or deployed to make agents durable. This is the **same shape** as batch-13's HumanLayer counter ("we don't need a new cluster for this", loops on stock CI) and batch-14's Netflix counter to `pat-agent-memory-layer` (markdown in a Git repo). That now makes **three** practitioners saying a proposed infrastructure layer is really a convention over existing infrastructure.
   - *And the agent loop itself is not durable at all:* in-memory short-term state, sub-500 ms budget, no checkpoint/resume, no replay of the agent's own reasoning. The durability is in the domain events, not in the execution. Per instruction, nothing was coined and no signal was homed on the candidate.
2. **`pat-agent-memory-layer` (uncoined) — second explicit counter.** `sig-sla-budget-caps-agent-design` records a production system that **rules long-term agent memory out by SLA** and gets its "memory" entirely from domain projections. Joins the Netflix markdown-in-Git counter from batch 14. Worth putting in the pattern's brief if it is coined: the memory layer is contested at the latency boundary and at the tooling boundary.
3. **Caption garbles.** "even so system"/"even driven"/"even sourcing" → *event-sourced* / *event-driven* / *event sourcing* throughout; "agent AK processing" → *agentic processing*; "materials view" → *materialized view*; "regax"-style noise absent here but "no sequel" → *NoSQL*; "KYC complaining" → *KYC compliance*; "risk code" → *risk score*; a stray interjection ("careful") is an audience/AV artifact. None of these affect entity identity — the architecture terms are all standard and internally consistent.
4. **`el-semantic-layer` reuse is deliberate and slightly stretched.** The speaker's "semantic layer" is a denormalized materialized view for agent consumption, whereas Daga's (batch 2) is a curated KPI/metric definition layer and Neo4j's (batch 10) is ontology-backed. Same term, three altitudes. I reused rather than coined `el-agent-materialized-view` because the *function* — one curated, agent-facing surface in front of messy sources — is identical; if you disagree, coin the split at seeding and downgrade this file's edge to prose.
5. **`el-jury-judge-workflow` merge-check.** That element (batch 6) is an *evaluation* construct — multiple judges scoring an output. Here the third agent is a **runtime decision-maker** in the transaction path, not an evaluator. I coined `el-fan-out-agent-consensus` for the runtime shape and linked it to the eval one; collapse them at seeding if you read "jury/judge" as topology-not-purpose.

The strongest three are `sig-agents-scoped-to-the-gray-zone`, `sig-event-store-is-the-agent-context-layer` and `sig-sla-budget-caps-agent-design`; the other two are architecture description and can be dropped to prose if your signal bar is high.
