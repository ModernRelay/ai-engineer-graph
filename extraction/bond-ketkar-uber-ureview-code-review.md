| `el-ureview` | uReview | product | harness | Uber's in-house multi-agent code review engine. Surfaces — GitHub, Phabricator, and the **agent loop** — feed one uReview service that takes review requests, ingests user feedback and routes; multiple **generators** tuned for different cost/performance points (a single-file "find the logic bugs" reviewer; a multi-file deep reviewer per monorepo with its style guides and anti-patterns baked in; few-shot **AI linters** that fetch deterministic context and apply rules; **custom team agents** linked to a knowledge base, past PRs and a review skill), plus pluggable third-party review systems for benchmarking; then **post-processing** that rates, categorizes, filters and deduplicates so engineers get only high-confidence actionable comments. Built in-house for Phabricator support, inner-loop parity for agents, distributed ownership, risk/complexity-aware routing, and guaranteed security/compliance review on everything |
| `el-review-observability-ladder` | The review observability ladder | technology | harness | uReview began as one per-file logic-check prompt, a thorough-review agent and a dispatcher, observed only by cost, an NPS survey, Google Forms and Slack support — quality-to-cost "all over the place." Step one: classify the **sentiment of developer replies** to review comments and categorize them, exposing whole classes of fixable bugs. Step two: track **address rate** — does the developer act on the comment? Step three: a **runtime profile of the agent trajectory** (tool calls, thinking) explaining why it did what it did, used to tune runtime and performance. Lessons: "the model doesn't know that it's wrong" (always 100% sure), needs each team's style guide and anti-patterns baked in, and needs **guardrails on what not to waste turns on** because review has a time budget. Result vs the naive version: cost −60%, accuracy +70%; 25K comments/week, 10% get feedback, only 4% of PRs any negative feedback, 67% address rate, ~¾ of high-severity issues addressed |
| `el-review-customization-via-ownership` | Review customization through the ownership model | concept | harness | Hundreds of teams each with their own review conventions cannot be centrally managed, so uReview piggybacks on Uber's code-ownership model: customizations (rules, AI linters, custom agents, skills) are **co-located next to the code** so teams can keep updating them; **smart deterministic routing** decides which team gets which review kind, model and generators; and the observability — trajectories, address rate, sentiment — is **surfaced back to rule authors** ("I wrote this rule but my developers don't like it — let me update it") and to platform contributors. Writing a skill was easy (ask Claude to read your past PR reviews and write one); running those skills at scale with consistent quality and low cost took many iterations from the platform team and every contributing team |
| `el-agent-review-cavitation` | Agent review cavitation | concept | harness | The inner-loop failure mode: when an agent receives a low-quality review comment it "fixes" it, gets re-reviewed, and has to fix backwards — oscillating on a bad comment. So for agent consumers the accuracy bar must go *up*, not down, even though agents are "more than happy to fix 100 nits" that would frustrate a human. Agents in the loop get the same rules and review as humans; the interface and the accuracy threshold are tuned per audience |
| `el-expanding-the-outer-loop` | Expanding, not killing, the outer loop | concept | harness | With engineers authoring less and a short path to a percentage of code landing with automatic approval, the question becomes whether to remove the human from review. The catch: the human feedback that flowed back into uReview is what made review high quality, so removing it invites quality degradation and slop. The industry is coalescing instead on moving human responsibility **up a layer** — the agent writes and increasingly reviews at the implementation level (performance, API compatibility); the engineer's outer loop becomes architecture, domain expertise and product thinking |
