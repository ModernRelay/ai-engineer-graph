Inline completion → chat → vibe coding gave her maybe 10–20%; teams practising **frontier development** — hands-off coding (humans write 1–2% of the code), infrequent interaction (agents run for hours), minimal idle time (parallel agents through a backlog) — show a **median 4.5×, sometimes >10×** productivity gain. | `el-five-frontier-habits` | The five frontier habits | concept | harness | Interviews across the pilots found habits, not a sprint. (2) **Slow down to speed up.** (3) **Feed agents, don't babysit them.** (4) **Make intent explicit** — behaviour-driven development and specs; iterate with the model on a document, not on code spread across a code base. (5) **Shift testing left** — linters, unit/integration/performance/security tests, and locally-run deterministic **mock services** so the agent's feedback loop is fast and entirely on the laptop; "good hygiene we should have done all along, but now the ROI is finally high enough" |
| `el-slow-down-to-speed-up` | Slow down to speed up | concept | | Almost every interviewed team reported productivity going *down* while adopting the new way of working: real engineering work in the code base has to come first — building agent context, improving tool error messages so the model knows why it failed, new tools and MCP servers, restructuring the code base for agent navigation, even changing language (teams struggling with untyped Python/JavaScript moved to TypeScript; Rust popular for its compiler errors). Organizationally: leaders — the speaker included — say "you have the AI tools, why aren't you going faster?"; the answer is two months of investment and hard habit changes, and not expecting all teams in a massive org to be frontier teams at once |
| `el-feed-agents-dont-babysit` | Feed agents, don't babysit them | concept | harness | Why vibe coding cannot produce 4–5×: a back-and-forth conversation keeps the human in the loop, waiting 30–60 seconds per turn, unable to run agents in parallel or "clone yourself." Feeding means giving the agent what to do *and how to self-validate*, so it self-corrects and only comes back when it meets a quality bar — compiles, passes tests, is testable, has coverage — and then putting that bar into the steering file so it happens every time without prompting. The mechanism behind hours-long runs and parallelism |
| `el-flowmaxxing` | Flowmaxxing and the hidden load | concept | | The burnout risk of frontier development: engineers staying up late chasing the perfect prompt that will run an agent for hours overnight so a change is ready in the morning; cognitive load from running multiple agents in parallel and constantly switching terminal tabs; and reviewing AI output being harder than writing it for many — senior engineers have spent careers reviewing others' code, early-career engineers do not have that muscle yet, so review feels like more load than authoring |
| `el-decision-speed-bottleneck` | Decision speed is the new bottleneck | concept | | Writing code manually used to be the bottleneck; inside Amazon the speed of decision-making now is. When a product took 9–12 months to build, two months to decide and two months to approve the launch washed out; with code taking one to two months, those review and approval processes are the long pole, and frontier teams spend more time making decisions than writing code.
